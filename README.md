# BPMSoft IntelliSense

Расширение для VS Code / Cursor: автодополнение, навигация, подсказки и диагностика AMD-схем BPMSoft / Creatio.

Работает в JavaScript-файлах (`onLanguage:javascript`). После открытия workspace индексирует `Pkg`, `Autogenerated` и платформенный UI.

Для C# в `Pkg` и `Autogenerated` нужен `BPMSoft.Configuration.Dev.sln`: языковой сервер C# без solution не поднимает проект. Файл `.csproj` есть всегда; если `.sln` рядом нет, расширение создаёт минимальный solution рядом с csproj. Путь считается от открытой папки: корень приложения, `BPMSoft.Configuration`, `Pkg` или пакет. Если расширения C# нет, предлагается установить **C#** (`ms-dotnettools.csharp`, вместе с ним **.NET Install Tool**).

## Что умеет

### Автодополнение

Пишите код как обычно — подсказки появляются по `.`, `$`, `"`, `'`, `(` и при вводе идентификатора.

| Контекст | Что предлагается |
| --- | --- |
| `this.` | Методы, properties, атрибуты (`$Name`), **миксины** схемы/иерархии, колонки entity, `entitySchemaName` / `entitySchema`, `sandbox` / `Ext` / `BPMSoft` |
| `this.MixinName.` / `this.mixins.MixinName.` | Методы и свойства этого миксина |
| `this.$` | Атрибуты схемы; колонки `entitySchemaName` только у карточки (`EDIT_VIEW_MODEL_SCHEMA`, `conf/content` + `Pkg/**/Schemas/{Entity}/metadata.json`). У секции (`MODULE_VIEW_MODEL_SCHEMA`) колонок объекта в `this.$` / `get` / `set` нет |
| `this.get("` / `this.set("` | Имена атрибутов |
| `this.sandbox.publish("` / `this.sandbox.subscribe("` | Сообщения из `messages` схемы/иерархии и ядра `NavigationModule` |
| `diff` / `methods` → `bindTo: "` (ключи с кавычками или без) | Методы и атрибуты схемы/иерархии |
| `this.$Lookup.` / `this.get("Lookup").` | Поля lookup/enum: `value`, `displayValue` |
| `this.sandbox.` | `publish`, `subscribe`, `loadModule`, …; после `publish`/`subscribe` сразу список сообщений |
| `this.Ext.` / `this.BPMSoft.` | Тот же API, что у глобальных `Ext` / `BPMSoft` |
| `BPMSoft.` | Enums (`SysValue`, `DataValueType`, …), классы, `configuration.Structures.*` из **этого** проекта (`conf/content`) |
| `Ext.` | `isEmpty`, `String`, `Array`, … (+ разбор `Resources/ui/ExtJs`) |
| Идентификатор (`BPM…`) | `BPMSoft`, `Ext`, `define` |
| Внутри `methods: { }` или тела `Ext.define` | Сниппеты **override** родительских методов (`@inheritdoc` + `@overriden`) |

Индексированные подсказки поднимаются выше word/history (см. `bpmsoft.preferIndexedCompletions`).

### Переход к определению

`F12` / Go to Definition:

- `this.foo`, `this.$Foo`, `this.get("Foo")` / `this.set("Foo"` — в схему, родителя, миксин или entity
- `this.MixinName.foo` / `this.mixins.MixinName.foo` — в миксин
- `this.sandbox.publish("Msg")` / `this.sandbox.subscribe("Msg")` — в блок `messages` схемы, родителя, миксина или в `NavigationModule`
- `bindTo: "getVisible"` / `bindTo: "IsEnabled"` в `diff` и в `methods` (в т.ч. `controlConfig`) — в метод или атрибут схемы/иерархии
- `this.sandbox.publish` — в исходник sandbox
- `BPMSoft.generateGUID` / `BPMSoft.GUID_EMPTY` / `BPMSoft.SysValue.*` (и другие извлечённые `BPMSoft.*` / `Ext.*`) — в `Resources/ui`
- Имя AMD-модуля / алиас из `define([...], function(Alias)` — в файл модуля

### Подсказка при наведении

Hover по тем же конструкциям: вид члена, документация, откуда пришёл (пакет / Autogenerated / mixin / entity).

### ESQ-запросы (EntitySchemaQuery / InsertQuery / UpdateQuery / DeleteQuery)

Расширение отслеживает переменные, созданные через `Ext.create("BPMSoft.EntitySchemaQuery", { rootSchemaName: "Contact" })` (а также `BPMSoft.InsertQuery`, `BPMSoft.UpdateQuery`, `BPMSoft.DeleteQuery`), и знает, к какому объекту относится запрос.

| Возможность | Где работает |
| --- | --- |
| Автодополнение имён объектов | `rootSchemaName: "` |
| Автодополнение колонок объекта | 1-й аргумент `addColumn`, `addSchemaColumn`, `addAggregationSchemaColumn`, `createColumnIsNullFilter` / `createColumnIsNotNullFilter`, `createColumnBetweenFilterWithParameters`, `setParameterValue`, `setColumnValue`; 2-й аргумент `createColumnFilterWithParameter` |
| Пути через lookup | `"Account.PrimaryContact.Name"` — каждый сегмент дополняется по метаданным объекта, на который ссылается lookup-колонка |
| Автодополнение по `esq.` | Методы и свойства классов запросов из платформенного UI |
| Hover и `F12` | По `rootSchemaName` — к объекту (`conf/content` / `metadata.json`); по имени колонки — к её описанию |
| Диагностика | Предупреждение «Колонка … не найдена в объекте … (conf / metadata)», если объект проиндексирован, а колонки в нём нет |

Колонки берутся из `conf/content/{Entity}.js` и `Pkg/**/Schemas/{Entity}/metadata.json` (как и для `this.$`).

### Диагностика отсутствующих `this.*`

Только для AMD/Ext модулей, которые расширение умеет разобрать. Комментарии и строки не проверяются.

| Обращение | Когда | Уровень | Quick Fix (лампочка / `Ctrl+.` / `Cmd+.`) |
| --- | --- | --- | --- |
| `this.foo(` | метода нет в схеме и иерархии | ошибка | создать метод |
| `this.foo` без `(` | имени нет ни у какого члена | предупреждение | создать property **или** метод |
| `this.$Foo`, `this.get("Foo")`, `this.set("Foo"` | нет атрибута `Foo` | предупреждение | создать атрибут (только в схемах страниц) |
| `this.mixins.Name` | миксина `Name` нет в `mixins` текущей схемы и иерархии | ошибка | — |
| `this.mixins.Name.foo` / `this.Name.foo` | у миксина нет такого метода или свойства | ошибка | — |
| `this._foo` / `this.mixins.Name._foo` | член с `_` объявлен в **другом** файле | предупреждение | — |
| `this.sandbox.publish("Msg")` | `Msg` нет в `messages` схемы/модуля/иерархии **или** направление не `PUBLISH` / `BIDIRECTIONAL` | предупреждение | — |
| `this.sandbox.subscribe("Msg")` | `Msg` нет в `messages` **или** направление не `SUBSCRIBE` / `BIDIRECTIONAL` | предупреждение | — |
| `diff` / `methods` → `bindTo: "foo"` | метода/атрибута `foo` нет в схеме и иерархии | предупреждение | создать метод **или** атрибут `BOOLEAN` |

«Существует» = текущий файл + `Structures` (stack / `structureParent`) + миксины + колонки entity (`conf/content/{Entity}.js`, плюс колонки из `Pkg/**/Schemas/{Entity}/metadata.json`, подписи из `Pkg/**/Resources/{Entity}.Entity/resource.ru-RU.xml`) + `BPMSoft.BaseSchemaViewModel` (скрытый родитель SchemaBuilder) + `extend` платформы + runtime `sandbox` / `Ext` / `BPMSoft`. Если колонка есть и в conf, и в Pkg, берётся conf (включая описание).

Не помечаются: `this.callParent`, `this.mixins` (сам объект), динамика (`this.get(name)`, `this.sandbox.publish(name)`, `this[expr]`), `this._foo` **в том же файле**, где член объявлен. Если в схеме или родителе есть блок `mixins`, локальные имена доступны как `this.Name` и `this.mixins.Name`; методы миксина — через точку. Сообщения `sandbox` ищутся в `messages` текущей схемы/модуля, родителей, миксинов и в ядре `NavigationModule`.

Вставка в **текущий файл**:

- схема: в `methods` / `properties` / `attributes` (секция создаётся, если её нет)
- Ext-модуль: method/property в тело `Ext.define`; атрибуты не предлагаются

Шаблоны: `foo: function (args) { }`, `foo: null`, атрибут с `dataValueType: BPMSoft.DataValueType.TEXT`. После вставки индекс обновляется сразу, без сохранения.

### Стиль JavaScript

Для редактируемых JS (не `Autogenerated`, не `Resources/ui`, не `conf/content`). Отключается настройкой `bpmsoft.styleDiagnostics`.

| Правило | Уровень | Quick Fix |
| --- | --- | --- |
| Стиль скобок **K&R** (`if (x) {`, `} else {`) — иначе Allman | предупреждение | перенести `{` / `else`/`catch`/`finally` на ту же строку |
| Объявление через `var` | предупреждение | заменить на `let` или `const` |
| Присваивание в переменную, объявленную как `const` (`x =`, `x++`, `+=`) | ошибка | заменить `const` на `let` |
| Цепочка `if` / `else if` / `else` **больше 3 ветвей** | предупреждение | заменить на `switch`, если все условия — `===` / `==` с одной и той же переменной |
| `==` / `!=` (кроме `== null`) | предупреждение | заменить на `===` / `!==` |
| Неиспользуемые переменные и параметры | предупреждение | — |
| Код после `return` / `throw` / `break` / `continue` | предупреждение | — |
| `switch`: дублирующий `case`, провал без `break` | ошибка / предупреждение | добавить `break` |
| Тело `if` / `for` / `while` без `{ }` | предупреждение | обернуть в скобки |
| `debugger`, `console.log` / `warn` / `error` / … | предупреждение | удалить |
| `x === NaN` | предупреждение | `Number.isNaN(x)` |
| Повторяющиеся ключи объекта (`methods` / `attributes` / `messages` и любые литералы) | ошибка | — |
| В `diff` несколько блоков с одной и той же парой `operation` (`merge` / `move` / `remove` / `insert`) и `name` | ошибка | — |
| Неиспользуемые **methods / attributes / messages** текущей схемы | предупреждение | удалить объявление. Атрибут проверяется, только если в конфиге есть лишь `dataValueType` / `value` / `type`; `lookupListConfig`, `dependencies`, `isRequired`, `caption` и прочие ключи — не проверяются |
| Локальные переменные и параметры — **camelCase** (допустим `_camelCase`) | предупреждение | переименовать. Параметры фабрики `define(..., function (A, B)` не проверяются |
| Объявленные методы (`function`, `methods: { ... }`, методы класса) — **camelCase** | предупреждение | переименовать |

Не помечаются как неиспользуемые: override методов/атрибутов/сообщений родителя, миксина, колонок entity и ядра `NavigationModule`; обращения `this.foo` / `this.$Foo` / `get`/`set` / `sandbox.publish|subscribe`; строковые литералы в том же файле (`bindTo: "onClick"`). Параметры фабрики `define(..., function (A, B)` не считаются неиспользуемыми. Имена с префиксом `_` тоже пропускаются.

Мутация полей объекта (`const obj = {}; obj.x = 1`) не считается нарушением `const`. Quick Fix на `switch` не предлагается, если условия не сводятся к сравнению одной переменной с литералами / константами.

### Стиль C#

Для редактируемых `.cs` (включая `Autogenerated/Src`, потому что именно эти файлы открывает C# Dev Kit). Не проверяются `obj/` и `node_modules`. Тот же флаг `bpmsoft.styleDiagnostics`. Скобки — **Allman** (наоборот от JS).

| Правило | Уровень | Quick Fix |
| --- | --- | --- |
| Стиль скобок **Allman** (`if (x)` и `{` на следующей строке) — иначе K&R | предупреждение | перенести `{` на новую строку |
| `} else` / `} catch` / `} finally` на одной строке | предупреждение | перенести keyword на новую строку |
| Цепочка `if` / `else if` / `else` **больше 3 ветвей** | предупреждение | заменить на `switch`, если все условия — `==` с одной переменной |
| `switch`: дублирующий `case`, провал без `break` / `return` / `throw` / `goto` | ошибка / предупреждение | добавить `break` |
| Тело `if` / `else` / `for` / `foreach` / `while` без `{ }` | предупреждение | обернуть в скобки |
| Методы и свойства — **PascalCase** | предупреждение | переименовать |
| Приватные поля — **`_camelCase`** | предупреждение | переименовать (`name` → `_name`) |
| Локальные переменные и параметры методов — **camelCase** | предупреждение | переименовать |
| Классы / структуры / enum / record — **PascalCase**; интерфейсы — **IPascalCase** | предупреждение | переименовать |
| Пустой `catch { }` | предупреждение | — |
| `== null` / `!= null` | предупреждение | `is null` / `is not null` |
| `async Task` без суффикса `Async` | предупреждение | добавить `Async` |

Компактные автосвойства `int Name { get; set; }` на одной строке не требуют Allman. Объектные и коллекционные инициализаторы (`new Foo { }`, `= { }`) тоже не проверяются.

### Git Flow

Проверка текущей git-ветки на соответствие модели Git Flow (`main` / `develop` / `sprint/x.x.x` / `release/x.x.x` / `feature/*` / `bugfix/*`). Нарушения — в статус-баре внизу окна (значок предупреждения, при наведении — список всех найденных проблем); молчит, если всё в порядке. Обновляется при смене активного файла и при возврате фокуса в окно VS Code (смена ветки в терминале/внешнем git-клиенте перехватывается так).

| Проверка | Надёжность |
| --- | --- |
| Имя ветки соответствует одному из паттернов | точная |
| `main` не содержит коммитов, которых нет в `develop` (не считая merge-коммитов — обычный `develop → main` мердж всегда добавляет такой коммит только в `main`, это не нарушение) | точная, если ветки резолвятся (локально или как `origin/...`) |
| `feature/*` создана от `sprint/*`, `bugfix/*` — от `release/*` | эвристика по `git merge-base`, может ошибаться на сложной истории — отключается отдельно |

Порядок шагов самого процесса (например, что `sprint/x.x.x` смержили в `develop` раньше, чем создали `release/x.x.x`) не проверяется — это не восстановить из истории git постфактум, а `rebase` может её переписать.

Настройки: `bpmsoft.gitFlowDiagnostics` (общий выключатель), `bpmsoft.gitFlow.mainBranch` / `bpmsoft.gitFlow.developBranch` (если вместо `main` используется `master` и т.п.), `bpmsoft.gitFlow.checkBranchParent` (отключить только эвристическую проверку родителя ветки).

### Проверка пакета

Раздел «Пакеты» naming-guidelines.md требует настроить перед началом работы «Текущий пакет» (`CurrentPackageId`), «Префикс названия объекта» (`SchemaNamePrefix`) и «Издатель» (`Maintainer`) — три системные настройки BPMSoft. У расширения нет подключения к БД системы, поэтому эти три значения задаются вручную во вкладке **Package Settings** (контейнер BPMSoft Settings, клик по строке открывает поле ввода) и используются для проверки пакетов, которые вы редактируете, по их собственному `descriptor.json` (`Maintainer`, имя пакета).

| Проверка | Что означает |
| --- | --- |
| Префикс пакета (использует общую настройку `bpmsoft.namingPrefixes`) | Имя пакета (`GoTracker`, `NauLogging`, …) не начинается ни с одного из настроенных префиксов — похоже, что редактируется пакет чужого стрима |
| Издатель (`bpmsoft.expectedMaintainers`) | `Maintainer` в `descriptor.json` пакета не входит в список настроенных — пакет стороннего издателя, изменения могут требовать согласования |

«Текущий пакет» — пока только справочное поле (показывается в Package Settings), не участвует в проверке: расширение не создаёт новые схемы «в текущий пакет» так, как это делает система, поэтому автоматически проверить соответствие нечем. Нарушения — в статус-баре, рядом с индикатором Git Flow.

### Команда

**BPMSoft: Rebuild Index** (Command Palette) — полная переиндексация `Pkg` + `Autogenerated` + UI. В статус-баре: число модулей и тип layout.

## BPMSoft Explorer

Отдельный контейнер в Activity Bar (значок BPMSoft) — альтернатива стандартным Explorer / Outline / Timeline с пониманием специфики BPMSoft-схем, которого у стандартных панелей VS Code нет.

### Packages

Дерево пакетов workspace: `Data` / `Files` / `Resources` / `Schemas` / `SqlScripts` / `Assemblies`. Подгружается лениво (по разворачиванию узла, не сканирует всё сразу). Иконка схемы — по её реальному типу (`ManagerName` из `descriptor.json`, для `ClientUnitSchemaManager` — ещё и по `SchemaType`: Page / Section / Detail / Module / …). Пакеты, в которых из содержимого есть только `Files` (типичный признак «коробочного», не кастомизированного пакета), показываются приглушённым цветом. Проблемы именования (см. Naming Issues) подсвечиваются прямо в дереве, включая «всплытие» предупреждения вверх до уровня пакета.

### ViewModel Outline

Свой Outline для активной **модели представления** — сознательно только для неё: показывает дерево, только если открытый JS-файл — настоящая view-model-схема (Page / Section / Detail и их варианты, по `SchemaType`); для Module-схем, миксинов, констант и не-JS файлов дерево пустое (для них — соседняя вкладка **Outline**, см. ниже). В отличие от стандартного `this.`-автодополнения показывает не только собственные члены схемы, но и разбирает специфичные для BPMSoft секции конфига:

- **Атрибуты / Свои методы / Унаследованные методы / Миксины / Модель данных (`entitySchema`)**.
- **Diff** — настоящее дерево (`insert` / `merge` / `remove` / `move`), а не плоский список: `insert` вкладывается в `parentName`, `remove` с `properties` корректно распознаётся как удаление конкретных свойств, а не всего элемента. У каждого элемента — «Заполненные свойства/события» и **«Доступные, но не заполненные»**: реальный список конфигов, которые понимает платформенный control — резолвится через `itemType` (диспетчер `ViewGeneratorV2.generateStandardItem` → реальный `Ext.define`-класс в `Resources/ui/BPMSoft/controls/**`) либо, если `itemType` нет (обычное поле с `bindTo`), через `dataValueType` связанного атрибута (`generateEditControl`). Ограничение: список — только собственные свойства класса контрола, без обхода цепочки `extend`.
- **Бизнес-правила** — `rules` (ручные) и `businessRules` (из дизайнера) слиты так же, как их сливает платформа в рантайме; плюс **«Доступные свойства (BINDPARAMETER)»** — какие из `VISIBLE`/`ENABLED`/`REQUIRED`/`READONLY` для атрибута ещё не заняты.
- **Правила: мульти-действия**, **Детали**, **Встроенные модули**, **Доп. модели данных** (`dataModels`).
- **«Связано»** — атрибуты, детали, доп. модели данных, бизнес-правила и diff-элементы со общим `bindTo`/именем атрибута, а также diff-элементы (`DETAIL`/`MODULE`) со своей записью в `details{}`/`modules{}` по совпадению `name` — показываются друг у друга как кросс-ссылки, с переходом по клику.
- Развёрнутость узлов запоминается по каждому файлу отдельно (переключение между открытыми файлами не сбрасывает её). Toolbar: **Collapse All**, «…» → **Follow Cursor** (приближённо — данные это точки в файле, не диапазоны, подсвечивается ближайший элемент, не точное вхождение курсора).

### Outline

Простое зеркало стандартного Outline (через `vscode.executeDocumentSymbolProvider` — то же дерево символов, для любого языка с поддержкой символов, не только JS). Существует потому, что нативный Outline — системная панель, её нельзя перенести в свой контейнер. Toolbar: **Collapse All**, «…» → **Follow Cursor** (точный, по диапазону символа), **Filter on Type**, **Sort By** (Позиция / Имя / Категория).

### Timeline

История схемы (не одного файла — файл схемы + связанные ресурсы) из двух источников сразу: `git log` и стандартный VS Code Local History, смерджено по времени в одну ленту. У git-коммитов — насыщенный tooltip (автор, дата, полное сообщение, +/- статистика), diff по клику, «открыть коммит целиком». Toolbar: pin/unpin текущего файла, refresh, фильтр источников (git / local history), Local History: найти запись для восстановления.

### Open Schemas

Открытые вкладки редактора, сгруппированные по схеме (а не по файлу — у одной схемы обычно несколько файлов: `.js`, `.less`, `metadata.json`).

### Naming Issues

Схемы / SQL-скрипты, чьё имя не соответствует `naming-guidelines.md` (суффиксы `Page`/`PageV2`, `Section`/`SectionV2`, `Detail`/`DetailV2`, C# `Service`/`EventListener` — там, где платформа даёт однозначный маркер). Отдельный список + те же находки декорациями прямо в дереве Packages. Настраивается через `bpmsoft.namingDiagnostics` / `bpmsoft.namingPrefixes`.

**Объекты** (`EntitySchemaManager`-схемы, §2 гайдлайна) проверяются отдельно, включается через `bpmsoft.entityNamingDiagnostics`:

| Проверка | Детали |
| --- | --- |
| Код объекта: PascalCase, только английские буквы/цифры, префикс (`bpmsoft.namingPrefixes`) | Пропускается для замещений (`Parent.Name` = собственному имени, `ExtendParent`) — имя выбирали не в этом пакете |
| Код объекта: единственное число | Эвристика (оканчивается на `s`, кроме `ss`/`us`/`is`) + список исключений `bpmsoft.entityNaming.singularExceptions` (по умолчанию `Settings,Permissions,Statistics`); выключается отдельно через `bpmsoft.entityNaming.checkSingularName`, т.к. в английском нет надёжного синтаксического признака множественного числа |
| Технические префиксы/суффиксы (`Tbl`, `Entity`, `Field`) | И у объекта, и у колонок |
| Заголовок на русском и английском | `Resources/{Entity}.Entity/resource.{ru-RU,en-US}.xml`, `Item Name="Caption"`. Тоже пропускается для замещений — заголовок может быть унаследован от базовой (в т.ч. коробочной) сущности, не видной в `Pkg` |
| Уникальность кода по всей системе | Один и тот же код в нескольких пакетах — это нормально (механизм замещения), нарушение — только если **больше одного** пакета определяет код НЕ как замещение |
| Префикс у кастомных колонок | Та же логика, что у объекта |
| Булевы колонки — префикс-глагол | `bpmsoft.entityNaming.booleanPrefixes` (по умолчанию `Is,Has,Can`) |
| Колонки даты/времени — суффикс | `bpmsoft.entityNaming.dateSuffixes` (по умолчанию `On,Date`) |
| Lookup-колонка не должна заканчиваться на `Id` | Суффикс `Id` добавляется платформой автоматически на уровне БД/автогенерённого C# — второй раз в коде колонки его быть не должно |
| Избыточное повторение имени сущности в колонке своей же сущности | `Customer.CustomerName` → предлагается `Customer.Name` |

Не проверяется: наименование колонок «по смыслу значения» и «сущность, а не коллекция» — это про смысл, не про синтаксис, автоматически не отличить.

**SQL-скрипты** (§6 гайдлайна) — шаблон `{Object}_{Operation}{Description}` проверяется строго по гайдлайну (`Operation` — одно из `Create`/`Alter`/`Delete`/`Update`/`Insert`/`Drop`, плюс реально используемый в коде синоним `Remove`), плюс каждый `_`-сегмент — в PascalCase. **Важно**: на реальном коде порядок `{Object}_{Operation}` (а не наоборот) соблюдается не всегда — проверено на 279 реальных скриптах в двух установках, срабатывает на большинстве из них. Это осознанный выбор: проверка следует гайдлайну строго, а не подстраивается под то, как называли раньше.

Отдельно — мягкое напоминание про `_Temp`-скрипты (гайдлайн требует удалять их из пакета после успешного релиза): если `_Temp`-скрипт лежит в репозитории дольше `bpmsoft.sqlTempScriptMaxAgeDays` дней (по дате первого коммита, по умолчанию 30), подсвечивается как «возможно, забыли удалить». Это не точная проверка — расширению не видно, что реально накатано на среды, — а именно нэдж.

**Бизнес-процессы** (`ProcessSchemaManager`-схемы, §7 гайдлайна) проверяются отдельно, включается через `bpmsoft.processNamingDiagnostics`:

| Проверка | Детали |
| --- | --- |
| Код процесса: PascalCase, только английские буквы/цифры, префикс, обязательный суффикс `Process` | Суффикс проверяется строго по гайдлайну — на реальных данных соблюдается не всегда (служебные/фоновые процессы), это осознанно, как и с SQL-скриптами |
| Заголовок на русском и английском | `Resources/{Process}.Process/resource.{ru-RU,en-US}.xml`, `Item Name="Caption"` |
| Нет временных обозначений (`New`/`Test`/`Temp`/`Copy`/`V2`, …) | И в коде процесса, и в названиях элементов диаграммы |
| Action (задача) — название начинается с глагола | Слабая эвристика по окончанию слова (нет полноценной морфологии) — заведомо шумная, принято осознанно |
| Event (событие) — название описывает уже произошедший факт (прошедшее время) | Та же эвристика, проверяется и первое, и последнее слово (порядок «глагол+объект» на реальных данных встречается не реже книжного «объект+глагол»). Таймер-события (`StartTimerEvent`/`IntermediateCatchTimerEvent`) не проверяются — по гайдлайну у них своя логика именования (конкретные условия/расписание) |
| Exclusive-шлюз — рекомендуется закрытый вопрос | Проверяется как «заканчивается на `?`»; Parallel-шлюзы не проверяются |
| Sequence-поток (без условия перехода) не должен быть именован | Определяется по классу элемента диаграммы (`ProcessSchemaSequenceFlow` vs `ProcessSchemaConditionalFlow`), а не по тексту условия |

Диаграмма процесса читается из его собственного `metadata.json` (у Process-схем это обычный JSON, а не diff-DSL, как у клиентских схем) — элементы диаграммы ищутся по полю `BL1` (полное имя C#-класса), заголовки элементов — из `Resources/{Process}.Process/resource.ru-RU.xml` по ключу `BaseElements.{A2}.Caption`.

Не проверяется: содержательные требования к описанию Gateway/Event (текст «что произошло, при каких условиях»), единая терминология между процессами, отсутствие технических кодов/сокращений — это про смысл, не про синтаксис.

**Действие процесса / UserTask** (`ProcessUserTaskSchemaManager`-схемы, §8 гайдлайна) проверяются отдельно, включается через `bpmsoft.processUserTaskNamingDiagnostics`:

| Проверка | Детали |
| --- | --- |
| Код UserTask: PascalCase, только английские буквы/цифры, префикс, обязательный суффикс `UserTask` | Строго по гайдлайну (78% реального соответствия в двух установках), как и с процессами/SQL |
| Код UserTask начинается с глагола | В отличие от Action/Event у процессов — это английский **код**, не русский заголовок, поэтому вместо морфологической эвристики используется расширяемый список глаголов `bpmsoft.processUserTask.actionVerbs` (по умолчанию ~55 распространённых: `Get`/`Add`/`Update`/`Send`/`Calculate`/…) — точность заметно выше, чем на Process-элементах |
| Заголовок на русском и английском | `Resources/{UserTask}.ProcessUserTask/resource.{ru-RU,en-US}.xml`, `Item Name="Caption"` |
| Параметр: без технических аффиксов (`Tbl`/`Entity`/`Field`) | Та же логика, что у колонок объектов |
| Параметр: суффикс `Input`/`Output`, если параметров несколько | **Выключено по умолчанию** — на реальных данных (176 параметров в двух установках) суффикс не используется совсем (0%), включение почти всегда сработает. Включается через `bpmsoft.processUserTask.checkParameterDirectionSuffix`, если команда хочет начать соблюдать это правило |

Параметры UserTask хранятся в том же `metadata.json`, что и диаграмма процесса (`ProcessSchemaParameter`-элементы), заголовки параметров — там же в Resources, по ключу `Parameters.{A2}.Caption`. Автогенерируемый C#-код UserTask (в `Autogenerated/Src`) не проверяется отдельно — это лишь отражение тех же кодов параметров, а не отдельная поверхность именования.

**Данные** (схемы в `Data/`, §5 гайдлайна) проверяются отдельно, включается через `bpmsoft.dataNamingDiagnostics`:

| Проверка | Детали |
| --- | --- |
| Код: PascalCase, только английские буквы/цифры/`_` | Как везде |
| Код должен начинаться с имени своей целевой таблицы (`{TableName}_...`) | `TableName` берётся не эвристикой, а напрямую из `descriptor.json` (`Descriptor.Schema.Name`) — реальное имя таблицы/сущности, в которую сеются данные. Все варианты шаблона гайдлайна (`Lookup_X`, `{Table}_Data`, `SysSettings_{Code}`, `SysSettingsValue_{Code}`) сводятся к одному и тому же правилу, т.к. `Schema.Name` для Lookup-данных буквально `"Lookup"`, для настройки — `"SysSettings"` и т.д. Проверено на реальных данных: 0.6% срабатываний в lavka, 0% в netmonet |
| Нет «сырого» GUID/хеш-сегмента в коде | Гайдлайн просит убирать технические суффиксы после создания схемы данных (пример из гайдлайна: `SysModuleEditManager_1ecde34...`) — реально встречается (48 схем в lavka, в основном `SysModuleEdit_SysModuleEditManager_{guid}`) |
| Пара `SysSettings_{Code}` ↔ `SysSettingsValue_{Code}` | **Важно, по вашему указанию**: отсутствие настройки без значения — ошибка (реально может привести к 400 при чтении через `SysSettings.GetValue`), отсутствие значения без настройки — тоже. Сопоставление — не по имени папки, а по реальным данным: `Id` строки `SysSettings` должен совпадать со значением lookup-колонки `SysSettings` в строке `SysSettingsValue` (оба берутся из `data.json`). На реальных данных: 41 настройка без значения и 21 значение без настройки в lavka (часть второй категории может быть легитимным переопределением значения коробочной настройки, чьё определение не лежит в `Pkg`, — сообщение в тултипе честно об этом предупреждает) |

Не проверяется: «имя набора данных отражает таблицу, а не отдельную запись» (`ContactType_Data` vs `ContactType_Employee`) — смысловое различие, не синтаксическое.

## BPMSoft Settings

Второй контейнер в Activity Bar, для настроек и утилит расширения.

### Formatting

Форматирование JS / C# / SQL-скриптов (Prettier + свои фиксы стиля для JS, авто-фиксы отступов/скобок для C#, `sql-formatter` для `Pkg/*/SqlScripts/*.sql`) через стандартный Format Document (`Shift+Alt+F`, `editor.formatOnSave`). Управляется `bpmsoft.formatting.enabled`.

### Package Settings

Текущий пакет / префикс / издатель — см. «Проверка пакета» выше. Три строки, клик по любой открывает поле ввода.

## Откуда берётся `this.`

Используется `conf/content/{Schema}.js`:

```js
BPMSoft.configuration.Structures["LeadPageV2"] = {
  innerHierarchyStack: ["LeadPageV2Lead", /* … */, "LeadPageV2"],
  structureParent: "BaseLeadPage"
};
```

- Стек: слева база, справа самый производный (**правый побеждает**)
- `LeadPageV2Lead` → `Pkg/Lead/...` или `Autogenerated/Src/LeadPageV2.Lead.js`
- Голое `LeadPageV2` — верхний пакет
- `Pkg/*/Schemas/{Schema}` вне стека тоже учитывается
- `structureParent` обходится рекурсивно
- Если схемы нет в `conf/content`, родитель берётся из `descriptor.json` (`Parent.Name`) — дальше тот же алгоритм (стек / `structureParent` уже существующей в conf схемы)
- Миксины всех слоёв сливаются
- После схем добавляется `BPMSoft.BaseSchemaViewModel` (как в `ViewModelGeneratorV2`), затем `extend` из Structures (`BPMSoft.model.BaseViewModel`, …)
- Колонки `entitySchemaName` → `conf/content/{Entity}.js` и `Pkg/**/metadata.json` — только у карточки (`EDIT_VIEW_MODEL_SCHEMA`), не у секции (`MODULE_VIEW_MODEL_SCHEMA`). `this.entitySchemaName` / `this.entitySchema` есть и там, и там.

Если для схемы нет `conf/content/{Schema}.js`, родитель читается из `Pkg/.../Schemas/{Schema}/descriptor.json` (`Parent.Name`). Если `Parent.Name` совпадает с текущей схемой (замена из другого пакета / `ExtendParent`), этот шаг не обходится — копий той же схемы из других пакетов и так попадают в слои, зацикливания нет. Ищется дескриптор с **другим** `Parent.Name`. Уже посещённые имена и глубина > 50 тоже отсекаются.

### Модули (не страницы)

Свой файл + цепочка `override` / `extend` (например `BPMSoft.controls.Grid` → `Resources/ui/.../grid.js`).

Открыть: **Settings** → «BPMSoft IntelliSense», либо `settings.json` (User / Workspace).


## Какую папку открывать

Подойдёт любой из корней — `conf/`, `Resources/`, `Autogenerated/` находятся даже **вне** открытой папки:

- корень приложения (`bpmsoftdevelopment`, `suppliers2_190`, …)
- `BPMSoft.Configuration`
- `BPMSoft.Configuration/Pkg`
- `BPMSoft.Configuration/Pkg/{PackageName}`

Не открывайте родительский каталог с несколькими приложениями (например `crm-infrastructure`): расширение не активируется, если `BPMSoft.Configuration` лежит глубже открытой папки. Нужен корень конкретного приложения или `BPMSoft.Configuration` / `Pkg` / пакет.
